1. DISTRIBUTED TASK OFFLOADING KIYA HAI? (CLIENT-SERVER PARADIGM)
================================================================================
Jab kisi lightweight device (jaise battery-powered laptop ya low-spec client) par koi
heavy computational task chalana ho (e.g. 4K/1080p Video Rendering, AI Model Training,
ya Huge Matrix Inversion), to wo system garam ho jata hai aur ghanton laga deta hai.

- Task Offloading ka Concept:
  Client apna bhaari kaam (workload + assets) network k zariye kisi taqatwar remote
  worker machine (GPU Rig ya Server Node) ko bhej deta hai.
- Distributed Role Division:
    a) Client Node : Sirf UI chalata hai, parameters select karta hai, aur task offload karta hai.
    b) Server Node : Powerful hardware (NVIDIA GPU / High-Core CPU) par actual compute execute
                     karta hai aur finished result wapis client ko stream kar deta hai.
- Faida:
  Client ki battery bach jati hai, client freeze nahi hota, aur turnaround time 5x se 10x
  tak reduce ho jata hai.

2. PEER-TO-PEER NETWORKING, STATIC IP ADDRESSING & ROUTING (TASK 1)
================================================================================
Distributed computing mai machines ka aapas mai deterministic aur low-latency connection
hona zaroori hota hai:

- DHCP vs Static IP:
  DHCP mai router har dafa naya IP assign kar deta hai, jis se client ko server dhundna
  mushkil ho jata hai. Is liye peer-to-peer setup mai Static IP fix kiya jata hai:
    - Server Worker Node : 192.168.1.1 (Subnet: 255.255.255.0)
    - Client Laptop      : 192.168.1.2 (Subnet: 255.255.255.0)
- Localhost (127.0.0.1):
  Testing aur simulation k liye loopback interface istemal hota hai, jo physical NIC ko
  bypass karke pure memory speeds par TCP packets exchange karta hai.
- Firewall & Port Binding:
  Worker node port 5000 par TCP socket open karta hai (`INADDR_ANY` / `0.0.0.0`), taake
  LAN k tamam nodes se incoming connections accept kar sakay.

3. CUSTOM FRAMED BINARY + JSON SOCKET PROTOCOL DESIGN
================================================================================
TCP ek "Byte-Stream" protocol hai jisme koi built-in message boundaries nahi hotay
(Head-of-Line packet concatenation ka khatra hota hai). Is maslay ko hal karne k liye
humne ek Custom Binary + JSON Framing Protocol design kiya:

- 8-Byte Fixed Binary Header:
  Har packet k start mai exact 8 bytes ka structured header hota hai:
  +------------------+------------------+----------------------+
  | Magic (2 Bytes)  | Type (2 Bytes)   | Length (4 Bytes uint)|
  +------------------+------------------+----------------------+
  |   b"DC" (0x4443) | e.g. b"HS", b"FC"| Payload Size (N)     |
  +------------------+------------------+----------------------+

- Struct Packing (`!2s2sI`):
  `!` = Network Byte Order (Big-Endian)
  `2s` = 2 Bytes Magic ("DC" = Distributed Compute)
  `2s` = 2 Bytes Opcode (e.g., "HS" Handshake, "JS" Job Submit, "FC" File Chunk)
  `I`  = 4 Bytes Unsigned Integer (payload size up to 4 GB)

- Framing Protocol ka Faida:
  Receiver hamesha pehle exact 8 bytes read karta hai, length jaan leta hai, aur phir
  `recvall(length)` call karke exact payload receive karta hai. Koi message corrupt ya
  mix nahi hota.

4. RTT LATENCY PROBE AUR HARDWARE CAPABILITY DISCOVERY
================================================================================
Task offload karne se pehle client do aham cheezein pata lagata hai:

1. Round-Trip Time (RTT Ping Check):
   Client time $T_1$ par `PING_REQ` packet bhejta hai. Server foran `PONG_RESP` wapis karta
   hai jo client ko $T_2$ par milta hai.
   $$\text{RTT} = T_2 - T_1$$
   Yeh metric network delay (latency) batati hai. Gigabit LAN ya Localhost par yeh < 1 ms hoti hai.

2. Remote Capability Discovery:
   Handshake k waqt server apni hardware specs client ko report karta hai:
   - Operating System & Architecture (e.g. Windows 10 AMD64)
   - CPU Core Count (e.g. 4 Cores, 8 Threads)
   - NVIDIA GPU & NVENC status (e.g. Hardware Encoder Supported)
   Is discovery se client automatically optimal transcode preset aur bitrate decide karta hai.

5. REMOTE GPU EXECUTION ENGINE DAEMON & TASK SCHEDULING (TASK 2)
================================================================================
Server Node par chalne wala daemon multi-threaded execution engine par mushtamil hai:

- Listener Thread:
  Port 5000 par `socket.accept()` chalata hai aur har naye client k liye ek dedicated
  background worker thread spawn karta hai.
- Thread-Safe Task Queue:
  Jab multiple clients simultaneously jobs submit karte hain, to tasks ek thread-safe
  queue mai place ho jatay hain (`queue.Queue`). Mutex locks state race conditions ko roktay hain.
- Decoupled Storage:
  Incoming raw assets aur outgoing transcoded files `server_storage/` directory mai isolated
  tarah save hoti hain, taake koi naming collision na ho (`in_{task_id}_{filename}`).

6. HARDWARE VIDEO ACCELERATION: FFmpeg NVENC (GPU) VS CPU FALLBACK
================================================================================
Video encoding ek bohot computationally expensive process hai jisme discrete cosine
transform (DCT), motion estimation, aur entropy coding shamil hoti hai.

- NVIDIA NVENC (Hardware Acceleration):
  NVIDIA graphics cards par dedicated silicon chips hotay hain jo video transcode karne
  k liye optimized hotay hain (`-c:v h264_nvenc`). Yeh CPU cores ko 100% free rakhtay hain
  aur rendering ko 5x se 8x speedup detay hain.
- Multi-Threaded CPU Fallback (`libx264`):
  Agar worker node par dedicated GPU na ho ya NVENC driver initialize na ho sakay, to
  system dynamically CPU Multi-Threading mode mai switch ho jata hai:
  `-c:v libx264 -preset fast -threads 4`
  Is graceful degradation se system kabhi crash nahi hota aur task execute ho jata hai.

7. PARALLEL MATRIX COMPUTE & CUDA TENSOR WORKLOADS
================================================================================
Video k ilawa system generic parallel computation (Distributed Matrix Multiplication)
ko bhi support karta hai:

- Matrix Size $N \times N$:
  Client server ko matrix dimension (e.g. $1200 \times 1200$) aur iterations (e.g. 15) bhejta hai.
- Complexity:
  Do $N \times N$ matrices ko multiply karne ki theoretical complexity $O(N^3)$ hoti hai.
- Parallel Execution:
  Server multi-core BLAS/LAPACK threads ya CUDA tensor operations k zariye matrix chunks
  ko parallel execute karta hai, Frobenius norm compute karta hai, aur turnaround time
  client ko return karta hai.

8. DESKTOP CLIENT GUI ARCHITECTURE & THREAD SAFETY (TASK 3)
================================================================================
Client Application modern CustomTkinter framework par based hai jo dark-mode native
styling aur glassmorphism aesthetics deta hai:

- UI Thread vs Network Worker Threads:
  Tkinter ka main thread (`mainloop`) GUI rendering aur event handling k liye hota hai.
  Agar network operations (upload, transcode wait, download) main thread par kiye jayen,
  to window freeze ho jayegi aur OS "Not Responding" ka error dega.
- Solution (Thread-Safe UI Queue):
  Heavy network operations alag daemon thread (`threading.Thread`) par execute hotay hain.
  Progress updates ek thread-safe queue (`queue.Queue`) k zariye main GUI thread par
  post hotay hain (`_poll_ui_queue()`), jis se interface smooth aur responsive rehta hai.

10. DATA INTEGRITY & CRYPTOGRAPHIC SECURITY: SHA-256 CHECKSUMS
================================================================================
Network transmission k doran packet loss, bit flips, ya incomplete transfers se video
corrupt ho sakti hai. Is ko roknay k liye strict Cryptographic Verification implemented hai:

1. Upload Checksum:
   Client upload shuru karne se pehle local file ka SHA-256 hash nikalta hai:
   $$H_{in} = \text{SHA-256}(Asset)$$
   Server file receive karne k baad apna hash nikalta hai. Agar dono match karein to
   `[INTEGRITY] Verified` hota hai; warna file discard ho jati hai.

2. Download Checksum:
   Server render khatam hone par processed video ka SHA-256 hash packet mai bhejta hai:
   $$H_{out} = \text{SHA-256}(Output)$$
   Client download complete hote hi compute karta hai aur match hone par green
   **"SHA-256: VERIFIED ✔"** badge show karta hai. 100% Data Integrity Guaranteed!

11. EMPIRICAL BENCHMARKING: SPEEDUP (S), NETWORK OVERHEAD & AMDAHL'S LAW
================================================================================
Task 5 mai local execution aur remote offloading ka rigorous mathematical analysis kiya gaya:

1. Speedup Factor ($S$):
   $$S = \frac{T_{local}}{T_{remote}}$$
   Jahan $T_{local}$ client par direct render ka waqt hai, aur $T_{remote}$ total remote turnaround hai.
   Empirical testing mai 1080p video k liye $S = 5.23\times$ speedup achieve hua!

2. Total Turnaround Time Breakdown:
   $$T_{turnaround} = T_{upload} + T_{compute} + T_{download}$$

3. Network Overhead Fraction ($\eta_{net}$):
   $$\eta_{net} = \frac{T_{upload} + T_{download}}{T_{turnaround}} \times 100\%$$
   Chhoti files (480p) mai network overhead zyada hota hai (~45%), jabkay bari files
   (1080p) mai compute time dominate karta hai aur network overhead sirf ~15-25% reh jata hai.

4. Amdahl's Law Connection:
   Offloading ka overall speedup network transmission (non-parallelizable sequential part)
   se limit hota hai:
   $$S_{overall} = \frac{1}{(1 - P) + \frac{P}{S_{remote}}}$$
